## What this project is

Revamp CMS ("Revamp", for ET Oneworld) is a self-serve microsite builder for event pages — lets a non-technical event owner go from "Create Event" to a published microsite without Ops keying an intake form or a developer hand-coding sections. Full detail: [PRD.md](PRD.md).

Current implementation is a **static HTML/CSS/vanilla-JS prototype** — no framework, no build step, no backend. State lives in browser `localStorage`. Full detail: [Design.md](Design.md), [architecture.md](architecture.md).

## Facts worth remembering across sessions

- **Brand/target site**: ET Oneworld — "Published. The microsite is live at etoneworld.com" (from `dashboard.html`).
- **No backend, no auth, no real persistence** — everything is `localStorage`, per-page, per-event-id. Four different access patterns exist (`RevampCore.loadState/saveState`, two page-local direct variants, payments sub-app's own). Exception since 2026-09-24: the site editor's **template** pages save to IndexedDB (`editor-store.js`, db `revamp-editor`, store `sites`, key `site:<event id>:<template id>`) — pages are ~80 KB, too big to be comfortable in `localStorage`.
- **Three divergent CSS `:root` palettes** (`edit-event.css`, `create-event.html`, `Event_Listing.html`) — not yet unified. Don't assume one canonical color/token source when editing styles; check which file you're in. Fonts *are* unified as of 2026-09-21 though: `--font-body`/`--font-display` are Inter in every `:root` (colors/spacing tokens still diverge).
- **CMS chrome font is Inter** (`--font-body`/`--font-display` in every page's `:root`, as of 2026-09-21) — but the **microsite preview inside `custom_editor.html`** (the `.site-section` content) intentionally uses its own separate `--site-body-font`/`--site-display-font` tokens (default Manrope/Fraunces, overridden per template — see the per-template theming entry below). Don't "fix" those to Inter; they're deliberately independent so themed content matches each real ET template's typography.
- **Event context passes via URL `?event=<id>`**, not shared state — each page independently falls back to `EVENTS[0]` if missing.
- **Create Event wizard** (`create-event.html`) is a self-contained 4-step state machine (`STEPS`, `S.step`, `goStep(n)`), independent of `RevampCore`. Step 4 hands the draft to `custom_editor.html` via `localStorage['revamp.editor.handoff.v1']` + `?from=create`; the wizard has no preview step of its own.
- **`index.html` still has no `<meta charset="utf-8">`**, so its UTF-8 source (em/en dashes, `·`) renders as mojibake. `create-event.html` was fixed 2026-09-21, `dashboard.html` and `edit-event.html` on 2026-09-22; `index.html` is the last one outstanding.
- **All animation lives in [motion.css](motion.css)** (added 2026-09-22), linked from every page after its stylesheet, with the JS half (entrance cascade + stat count-up) in `app-shell.js`. Two easing tokens and three duration tokens; nothing animates layout properties. Add motion there, not in a page.
- **The in-event chrome comes from [app-shell.js](app-shell.js), nowhere else** (added 2026-09-22). `RevampShell.mount({section, eventId, ...})` draws the top bar *and* the rail and owns the section→URL routing table. Don't hand-write a `.topbar` or fill a `.rail` on a new page — give the page an empty `<header class="topbar" id="topbar">` and `<nav class="rail" id="rail">` and call `mount`. Pages outside an event (`index.html`, `Event_Listing.html`, `create-event.html`) deliberately have their own chrome and are not part of this.
- **Stack mismatch**: the original brief recommends Next.js + Tailwind; the team built static HTML/JS instead. This has not been confirmed as intentional — flagged as an open question in both PRD.md and architecture.md.

- **2026-09-22**: Motion layer. "Add the animation used in today's modern day industry." Added [motion.css](motion.css) — one file, linked from all 20 pages *after* their stylesheet so it wins — holding every moving part of the console, plus the JS half (`markEnter`/`countUp`) in [app-shell.js](app-shell.js).
  - **Two curves do all of it**: `--ease-out: cubic-bezier(.16,1,.3,1)` for anything arriving on screen, `--ease-spring: cubic-bezier(.34,1.4,.64,1)` for anything the user pressed. Durations are tokens (`--dur-1/2/3`), stagger is `--stagger`. Nothing animates layout properties — transform and opacity only, so a 400-row registrations table does not stutter.
  - **What moves**: content cascades in on first render (12px rise + fade, 34ms apart, capped at 7 steps); stat-tile numbers roll up from zero; progress bars grow from `scaleX(0)`; rail icons lift on hover; buttons lift and press; cards lift only if they are actually clickable; the tab underline grows from its centre; modals pop, drawers slide, backdrops blur; toasts spring in.
  - **The entrance window is the important trick.** `data-enter` goes on the content root *while it is still empty* (the page fills it later in the same task, so the children animate the first time they render) and comes off after 1.1s. Every re-render after that — a tab, a filter, a sort, a keystroke in the reporting search box — is instant. Without that window the table would re-animate on every keystroke. `mount()` only does it once per page, since the console re-mounts on every route change to move the rail's active item.
  - **Two bugs caught while testing the count-up**, both worth remembering if it is ever touched: (1) it must write the element's **first text node**, not `textContent` — the payment module's `.hud-val` is a number followed by a sibling `<span class="hud-sub">` ("2" + "2 live") and `textContent` flattened that span into plain text permanently; (2) `requestAnimationFrame` stops in a background tab, which strands a wrong number on screen, so a `setTimeout` at duration+400ms restores the exact original string regardless. Verified the settled values are byte-identical to the originals (912, 8.74 K, 10.4%, 3.87 Lacs) and that nothing is left stranded at `opacity:0`.
  - `prefers-reduced-motion` turns the whole thing off — `markEnter()` returns early so `data-enter` is never set and no count-up runs, and the media query at the bottom of `motion.css` zeroes every duration. Verified with Chrome's `--force-prefers-reduced-motion`: no `data-enter` in the DOM, exact values, page identical to before. Chrome geometry probe still reports the chrome as pixel-identical across pages, so none of this shifted layout.

Clicks in the canvas are captured at the iframe document and never reach the site (no navigation, no FAQ toggles).
